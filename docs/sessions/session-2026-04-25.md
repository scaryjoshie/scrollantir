## Architectural decisions

### 1. Location collection: full-precision GPS to Supabase

The earlier 4-decimal client-side egress snap (~10m grid) in
`IngestClient.sanitizeData` was removed. Coordinates ship to Supabase
at full device precision. Self-hosted single-user setup; sub-meter
fidelity is wanted for the place-matching layer (distinguishing a
specific classroom from the building, etc.). The dormant server-side
snap in `30_ingest_api.sql:585-589` is dead code (source-name
mismatch — `phone.location` vs `phone.location.reading`) and slated
for removal in a follow-up migration. See `concepts/location.md` for
the canonical position.

### 2. Places: query-time SQL match, NOT OS geofencing

Decided against Android's `GeofencingClient` API. Three reasons:

- **Schedule-awareness is impossible with OS fences.** "At Math 221"
  is only meaningful Mon/Wed/Fri 9–9:50; a fence is a circle, not a
  (circle, schedule) tuple.
- **Unlimited places.** GeofenceApi caps at ~100/app on Android.
- **Revisable without redeploy.** Renaming a place, nudging a radius,
  or changing a schedule is a single SQL UPDATE.

Activity-driven sampling already gives the battery win that geofences
would otherwise provide (STILL = no readings). See `concepts/places.md`
for the design.

### 3. Visit detection: STILL-overlap rule

For the "I walk *under* my dining hall on the way to class" pass-through
problem: a matched window only becomes a `place_visit` if there's at
least one overlapping `phone.activity.state = 'still'` span. Walking
through the dining hall = WALKING the whole time = no STILL overlap =
no false visit. Eating there = STILL for ≥ N minutes = visit confirmed.

Belt-and-braces: per-category minimum dwell (`food` 3 min, `class` 10
min, `residence` 0). The STILL-overlap rule is load-bearing; dwell is
garbage-collection.

### 4. Co-located places: don't try to disambiguate by place name

Gym + workspace at the same coords. Three options ranked:

1. **One place with `category: mixed` + behavioral aggregates.** The
   narrative "you spent 2h, 1.5h on phone, VS Code 1h, Reddit 20m" IS
   the workspace signature. Phone-light + sub-activity bursts IS the
   gym signature. Don't pre-categorize the place; let cross-source
   aggregates describe the visit.
2. **Prompt-on-arrival.** Existing `prompt-answer` infrastructure
   handles this. Defer to v2.
3. **Wifi BSSID side-channel.** Not v1.

### 5. Workout deriver: cadence + hard-anchors

For "am I logging sets vs. just glancing post-workout":

**Cadence (primary):** sliding 10-min window count of workout-app
foreground sessions. Workout = while window-rate ≥ 2; ends when two
consecutive windows dip below.

**Hard anchors (clamping):** define an upper bound — workout has
ended *no matter what* once any of these fire after the workout's
first session:

- Mac comes online (`mac.system.window` event) — laptop isn't at the gym.
- Gym `place_visit` EXIT.
- `phone.activity.state = vehicle` transition (driving home).
- (Soft fallback) sustained STILL > 25 min with zero workout-app sessions.

The hard anchors clamp the outer envelope; the cadence rule finds
the precise end inside it. Estimated precision ~95%+. Configuration
(workout-app package name) lives in `places.metadata.workout_apps`
JSONB on the gym row — self-contained.

This generalizes: "Mac online" is the right hard-stop signal for *any*
"am I doing focused thing X" derivation, not just gym.

### 6. AFK gating for activity-recognition noise

Phone Activity Recognition fires spurious transitions at night
(ambient vibration on bedside table). Filter: discard `phone.activity.state`
rows whose entire span lies inside a long phone-locked window.

**Architectural choice:** this is a SQL helper view
(`phone_activity_gated`), NOT a separate `awake_state` deriver.
Reasoning landed via correction during the session: each derivation
should pull the signal that natively answers its question — Mac AFK
for "actively using computer," phone unlock for "actively using
phone," activity recognition (gated) for "moving in the world." A
unified cross-device awake-state was premature abstraction; nothing on
the roadmap actually needs a single "is the human awake somewhere"
answer.

### 7. AFK-vs-derived-idle: derived-idle won (reversal)

Listed in [session-2026-04-23-aw-forwarder.md](session-2026-04-23-aw-forwarder.md)
as "switch to AW AFK." That decision was made against truncated data
(93% loss bug). Once the forwarder fix landed and real durations
flowed, AFK was over-aggressive. `dashboard/server/summarize.ts:16-20`
is the canonical model: `mac_active = mac_focus`, with idle = gaps in
`mac_focus ∪ phone_active` ≥ 2 min, clipped to "now."

The session-2026-04-23 chronicle has a postscript noting the reversal;
the body is preserved as a teaching example of how the wrong
conclusion fell out of buggy data.

### 8. Runtime rebuild: fresh `runtime/` folder, not extend `orchestrator/`

Decided against incremental extension of the bash-shaped `orchestrator/`
folder. Reasoning:

- The new shape (Python agent + scheduler + polling loop + Caddy +
  reserved-Postgres) doesn't fit the bash-shaped folder's mental
  model.
- The smallness of the existing code (~300 lines bash + Dockerfile)
  means there's almost nothing to lose by leaving it running
  unmodified during the rebuild.
- Fresh folder lets the new substrate stabilize before swapping
  systemd units.
- Naming collision avoided: `runtime/` cleanly replaces
  `orchestrator/`'s `runtime/` subfolder once the old folder retires.

Folder name `runtime/` (not `host/` — the Hetzner VM is the host;
`runtime/` is what runs on the host). Layout in
[rebuild-plan.md](../runtime/rebuild-plan.md).

### 9. Docker: one Dockerfile, not three

Within the docker-compose stack, only `agent/` ships custom code →
only `agent/` has a Dockerfile. Caddy and (future) Postgres use
official images (`caddy:2-alpine`, `postgres:16-alpine`) configured
via mounted Caddyfile + env vars + init scripts. The "Dockerfile per
service" instinct is wrong here.

### 10. Doc structure: subfolder taxonomy primarily component-aligned, with `concepts/` for cross-cutting

For agent-friendliness (predictable paths beat thematic groupings;
agents grep + path-search hard). Component subfolders (`android/`,
`mac/`, `dashboard/`, `supabase/`, `runtime/`) cover most tasks; the
`concepts/` slot holds genuinely multi-component features
(location, places, projects). `deferred/` and `sessions/` segregate
shelved designs and time-capsule chronicles.

## Postscript — 2026-04-26: self-host pivot

Follow-up scaffolding session. The big shift: decision #4 from
[rebuild-plan.md](../runtime/rebuild-plan.md) — *"postgres/ reserved
but not populated in v1; Supabase remains the data plane"* — was
reversed. `runtime/` v1 now adopts [self-host.md](../runtime/self-host.md)
in full: Caddy + PostgREST + local Postgres in the compose file from
day one.

**Why the pivot.** Two paths existed: (a) keep Supabase, write
derivers + PostgREST against it, redo everything when self-host
eventually lands; (b) populate `runtime/postgres/` now and do the
data-plane port once. (b) wins on net work and matches the project's
"own the data" principle. The agent shape (Python process + scheduler
+ Caddy reverse-proxy) was already pulling toward self-host; deferring
the Postgres half meant a second migration later.

**Other calls confirmed in the same session:**

- **Internal `runtime/` layout:** `runtime/{caddy,postgres,postgrest,app}/`.
  Single Python image at `runtime/app/`; `api` + `agent` are two
  compose services sharing the image with different `command:`
  directives. Pattern matches "Django + worker" / "FastAPI + RQ"
  conventions for shared-domain-layer Python monorepos.
- **Python package shape:** `app/src/scrollantir/{core,api,agent}/`.
  `core/` is the shared dependency layer (db client, models, deriver
  classes, llm runner). `api/` and `agent/` import from it; never
  from each other. Explicit `core/` boundary chosen over flat
  package-root layout for dependency-direction visibility.
- **Scheduler:** APScheduler in-process, in the agent container. No
  host cron, no in-container cron daemon. The agent process IS the
  runner for `forward()` (cron-fired) + `complete()` (60s poll) +
  daily-digest / weekly-report jobs. Pattern 3 from the rebuild
  plan, locked in.
- **Migrations tool:** `dbmate` against the live local Postgres.
  Lighter than sqitch, more ergonomic than plain bash.
- **Auth:** Path A from self-host.md — opaque bearer tokens validated
  server-side in RPCs. JWT migration deferred until browser/chat
  auth needs claims.
- **Postgres image:** `postgres:17-alpine` straight, no extension
  preload baked in. `pg_cron` is dropped — APScheduler obviates the
  use case. `earthdistance` is a contrib extension available via
  `CREATE EXTENSION` in init SQL when schemas land.
- **src/ layout** for the Python package (vs. flat) — catches
  packaging mistakes early and plays nicely with Docker layer caching.
