# Session 2026-04-28 — content detector hardening + GPS accuracy

End-of-session chronicle covering: shorts-detection false-positive fix
(three rounds of investigation, two committed fixes), `LocationWatcher`
priority bump from `BALANCED` → `HIGH_ACCURACY`, and the empirical
validation that produced both. Continuation of the post-cutover thread
from `session-2026-04-27.md`.

## TL;DR

- **`youtube.shorts` was attributing 100% of YouTube foreground time as
  Shorts** — even when the user was on Home / watch / search / etc.
  Driver was the previous "view-ID drift fix" (commit `41fb4aa`,
  2026-04-27) which adopted `reel_time_bar` as the primary detector ID.
  In current YouTube ReVanced, that ID is a full-screen template
  overlay present on every watch state, not a Shorts-only progress
  bar. Verified empirically: hourly aggregates showed YouTube
  foreground (39.2 min) ≈ shorts attribution (39.1 min) — exact 1:1.
- Fix landed in **three** commits today:
  1. `6521251` — LocationWatcher → PRIORITY_HIGH_ACCURACY
  2. `3651136` — bounds-check matched accessibility nodes
     (necessary framing fix; not sufficient alone)
  3. `1a57805` — drop `reel_time_bar`, require 2 consecutive matches
     (the actual completion)
- Today's bad shorts data wiped server-side (52 rows total across
  three deletes); LocationWatcher restart wiped the bad GPS data
  pre-rollout.
- **Phone-side local Room still has stale shorts events** until user
  taps **Settings → "Reset local data"** in the scrollantir app.

## Empirical chain that drove the diagnosis

The bug pattern was identified by hourly histogram of `phone.youtube.shorts`
duration vs `phone.system.foreground` duration filtered to
`app.revanced.android.youtube`:

| Hour (UTC) | YT foreground | shorts attributed |
|---|---|---|
| 03:00 | 39.2 min | 39.1 min |
| 04:00 | 22.4 min | 22.3 min |

Exact 1:1 ruled out coincidence. The `41fb4aa` commit was the obvious
candidate — that's when shorts began over-attributing. The drift
hypothesis behind that commit (that `reel_recycler` had been removed
from current YouTube) was wrong; the real issue was that
`findAccessibilityNodeInfosByViewId` returns matching nodes regardless
of layout position, so any "container present in tree" became "user is
on Shorts" — and `reel_time_bar` is present on all watch states with
full-screen template bounds.

## Fix 1 — bounds-check matched nodes (commit `3651136`)

**File:** `android/app/src/main/java/app/scrollantir/tracker/ContentDetectorService.kt`

Added an on-screen bounds gate to `hasNodeId()`. After
`findAccessibilityNodeInfosByViewId` returns candidate nodes, accept
only those whose `getBoundsInScreen()` rect intersects horizontal
screen range `[0, screenWidth]`:

```kotlin
nodes.any { node ->
    if (node == null) return@any false
    node.getBoundsInScreen(rect)
    !(rect.right <= 0 || rect.left >= sw)
}
```

`screenWidth` captured at `onServiceConnected` via
`resources.displayMetrics.widthPixels`. New field `@Volatile private
var screenWidth: Int = 0` added; pre-`onServiceConnected` falls back
to presence-only matching.

This mirrors DigiPaws' `ReelBlocker.isViewOpened` and is canonical
per Android docs. `isVisibleToUser` is **not** a substitute — per the
official API doc, "a more apt name would be
isPotentiallyVisibleToUser; nodes scrolled off-screen still report
true." Chrome's Android accessibility layer adds a custom `offscreen`
boolean derived the same way for the same reason.

**Why this wasn't enough on its own:** a separate empirical pass
revealed `reel_time_bar` reports full-screen bounds
`[0,0][1080,2424]` in *every* watch state in current ReVanced, so the
bounds check correctly let it through — but the underlying ID was
the wrong signal.

## Fix 2 — drop `reel_time_bar`, require 2-match start (commit `1a57805`)

### Part A: ID set replacement

Verified via `uiautomator dump` diff between two YouTube ReVanced
states:

- **Watch+shelf state** (paused on a video, Shorts shelf in view):
  only `reel_time_bar` present, full-screen bounds `[0,0][1080,2424]`.
  No other `reel_*` IDs.
- **Active Shorts player**: 13 unique `reel_*` IDs present, all with
  content-area bounds `[0,173][1080,2235]` (excluding 173px status
  bar + 189px nav bar on Pixel 9).

The IDs that proved Shorts-exclusive:

```
reel_recycler                  reel_player_overlay_root
reel_watch_player              reel_player_underlay
reel_player_page_container     reel_player_page_content
reel_watch_fragment_root       reel_video_interactions
reel_progress_bar              reel_player_footer_container
```

Replaced both YouTube and ReVanced rule's `primaryViewIds` with the
five most distinctive container IDs:

- `reel_recycler`
- `reel_watch_player`
- `reel_player_page_container`
- `reel_player_underlay`
- `reel_player_overlay_root`

`reel_time_bar` removed entirely. `reel_player_overlay` (no
`_root`/`_container` suffix) was a phantom — that bare ID doesn't
exist; only `_overlay_root` and `_overlay_container` do. Was never
matching anything anyway.

### Part B: 2-match start rule

Even with the right ID set, the first YouTube-open after the rule
update produced ~4.4 seconds of false attribution. Logcat showed:

```
12:28:00.183 MODE start: youtube.shorts        <- single transient match
12:28:01.576 no rule matched ...
12:28:03.006 no rule matched ...
12:28:04.569 no rule matched ...
12:28:04.570 MODE end:  youtube.shorts (4.4s, 3 misses)
```

Mechanism: during YouTube's app-open animation, the layout is in flight
and one of the `reel_*` IDs is briefly present + on-screen for ~234ms
before the actual watch UI replaces it. Then the regular miss-counter
correctly closes the session after 1.5s. But the transient attribution
still poisoned the data.

Added `MIN_MATCHES_TO_START = 2`: require two consecutive matches for
the same source within the throttled-event stream before declaring
MODE start. Single-event open-animation transients no longer trigger
attribution.

```kotlin
if (matched != null) {
    if (current?.source == matched) {
        // Already detecting this mode; refresh missCount.
        missCount = 0
        pendingMatchSource = null
        pendingMatchCount = 0
    } else {
        if (pendingMatchSource != matched) {
            pendingMatchSource = matched
            pendingMatchCount = 1
        } else {
            pendingMatchCount++
        }
        if (pendingMatchCount >= MIN_MATCHES_TO_START) {
            onDetected(matched, now)
            pendingMatchSource = null
            pendingMatchCount = 0
        }
    }
} else {
    onMiss(now)
    pendingMatchSource = null
    pendingMatchCount = 0
}
```

**Trade-off:** real Shorts viewing now takes ~500ms-1.5s after entering
the immersive player to fire MODE start (vs ~immediate before).
Acceptable since YT's content-changed events fire fast inside an active
player — second match arrives within one throttle window.

## Fix 3 — LocationWatcher → HIGH_ACCURACY (commit `6521251`)

**File:** `android/app/src/main/java/app/scrollantir/tracker/LocationWatcher.kt`

`PRIORITY_BALANCED_POWER_ACCURACY` falls back to wifi/cell
triangulation when GPS isn't already hot. Empirical result was
readings clustered at 80–150m accuracy with periodic spaz jumps when
the strongest wifi AP changed. Switched to `PRIORITY_HIGH_ACCURACY`
on both the single-shot anchor (`CurrentLocationRequest`) and the
periodic builder (`LocationRequest`). `setMinUpdateIntervalMs` was
already half the interval, so OS coalescing with concurrent
high-accuracy subscribers (Life360, Maps) is automatic — marginal
battery cost is small whenever another app is keeping the GPS chip
warm.

Accuracy gate left at 200m sanity floor. Once HIGH_ACCURACY data
shows the new distribution, can tighten further (likely to 50–80m).

## Stock YouTube applicability

The same code paths and the same ID list (`com.google.android.youtube:id/reel_*`)
are used for the stock YouTube package. **Untested empirically — the
test device only has ReVanced installed.**

Expected behavior is identical because:
- ReVanced is a patch fork of stock YouTube; the resource-id
  namespace is the same shape (just different package prefix), and
  ReVanced inherits the actual layout XML from stock.
- The bounds-check + 2-match-start logic is package-agnostic; it
  only depends on the raw mechanics of `findAccessibilityNodeInfosByViewId`
  and `getBoundsInScreen`, which are platform APIs.
- The five primary IDs (`reel_recycler`, `reel_watch_player`,
  `reel_player_page_container`, `reel_player_underlay`,
  `reel_player_overlay_root`) are present in stock YouTube per the
  DigiPaws ReelAppConfig, which is the upstream reference.

If stock YouTube ever does diverge (e.g., one of those five IDs
disappears in a stock-only update path), the existing
`detector.miss` diagnostic events will surface it — they include
full per-rule presence breakdowns of which primary IDs were searched
and which were absent in the live tree.

1. **Phone-side local Room cleanup** — the phone's `events` Room
   table still has 30+ false-positive `phone.youtube.shorts` rows
   from earlier today. The Today screen sums these into the daily
   shorts total and shows stale numbers. Tap **Settings → "Reset
   local data"** in the scrollantir app to clear it. Bearer token is
   preserved; only the local event queue is wiped.

2. **Server-side cleanup already done** — three DELETE statements
   ran during this session: location+activity wipe (14 rows), then
   two passes on shorts (37 + 15 = 52 rows). Total clean data
   timestamp on server is now post-`12:32` UTC.

3. **Instagram rule unchanged.** The `clips_viewer_*` IDs in the
   Instagram rule may have an analogous problem — we didn't dump IG
   to confirm. If IG-reels attribution starts looking 1:1 with IG
   foreground, the same diff-trees-and-replace-IDs approach applies.
   Telemetry will surface this in the same way the YouTube case
   surfaced (hourly histogram comparison).

4. **TikTok rule unchanged.** TikTok's "all feed all the time" rule
   uses the `*` wildcard sentinel that bypasses both bounds and
   ID checks — so neither fix nor regression risk applies. Stays
   matched as-is.

5. **Diagnostic safety net intact.** `detector.miss` events still
   fire (rate-limited 60s/pkg) with full view-ID dump and per-rule
   presence breakdown when no rule matches. If YouTube changes its
   tree again, the diagnostic data is already there for the next
   pass.
